# 开工前缺失点审查 v1.0

日期：2026-11-17。状态：分析与建议，待讨论；不自动修改已确认需求，不代表开始实现。

审阅依据：[需求基线 v1.1](首版需求确认单-v1.1.md)、[技术计划](技术方案与开发计划-v1.0.md)、[数据设计](数据设计与验收映射-v1.0.md)。

## 1. 审查结论

核心功能、数据结构方向、首页风格和主记账流程已明确，现阶段主要缺口是部分使用规则和交互边界，而不是尚缺完整的大功能。

- G01—G03 涉及使用方式或功能范围，建议在首页与输入流程实现前由用户决定。
- G04—G08 是既有功能的规则与规格补充，可先由开发方细化，再随相应阶段审阅。
- Excel 安卓适配、工具链、恢复事务、签名与升级属于计划中已有的验证任务，不重复列为新遗漏。
- 指纹锁、备份加密和支付方式属于可选扩展，不默认加入首版。

## 2. 需要用户决定的三个点

### G01：历史月份怎样查看

现状：首页明确为本月收支、结余与大类累计；明细支持日期筛选，但首页没有规定历史月份切换，也没有约定筛选后的合计展示。

影响：用户可能查到上月每笔记录，却不能在手机里直接看到上月对应的收入、支出和结余，只能导出分析。

建议：在首页月份位置增加轻量月份选择，默认当前月。选定历史月份后，各大类与顶部三项汇总同时更新；文案显示所查看的月份，避免把历史月份叫作“本月”。

统计月份与录入日期分开：记账日期仍默认今天，不因正在浏览上个月而自动补记到上个月；录入页清楚显示日期。

另一种有效选择：首版首页始终固定本月，历史内容只在明细和 Excel 中查看。这与现有基线一致，不是错误；需要明确选择。

### G02：新增记录时误点小类怎样快速纠正

现状：点小类即保存并回首页已确认；5 秒撤销目前只明确用于删除，没有明确用于新增。

影响：误点“饮食”而非“礼物”后，用户必须进入明细找到该笔再修改，影响快速记账。

建议：回首页时短暂显示“大类 / 小类 / 金额 · 撤销”，提供 5 秒撤销本次新增。保持点小类即保存的主流程，不增加保存确认。

该操作是撤回本次新增，与“删除后恢复原记录”是两种不同的撤销；实现和提示需要区分。普通修改是否也支持撤销，不自动扩展。

### G03：补记的时间精度与未来日期

现状：支持补记日期，发生时间包含时分秒，但没有明确是否允许修改具体时分，也没有规定未来日期。

影响：补记昨天下午的支出时，若只能改日期，可能留下今天录入时的时分；未来日期的记录也可能进入一个用户尚未查看的月份。

建议：日期、时分可编辑，默认当前值；首版只记录已发生事项，不允许未来日期，暂不扩展预记账。秒数由系统处理，无需用户手动输入。

这项建议会补充输入页面与日期校验规则，需要用户确认；不能把“允许补记”自行解释成已经同意未来日期或预记账。

## 3. 可以由开发方补齐的规格

### G04：Excel 完整快照与重复分析

现状：技术方案已有一致快照和稳定 ID，但缺少面向后续分析的“多次导出怎样使用”说明。

例子：先导出一笔 38 元记录，修改为 40 元后再次导出，直接把两份文件追加会变成 78 元。只按 ID 去重仍不能处理后来已删除、因此不再出现在新导出中的记录。

建议：明确每次导出是所选范围在导出时的完整快照。分析同一范围时以最新快照替换旧范围数据；使用不重叠的范围时才可直接拼接。跨范围、跨版本合并需考虑改日期、分类移动和删除，首版不承诺增量同步或自动合并。

保持已采用的 11 列不变，在导出说明中记录筛选范围、生成时间、笔数和模板版本。ID 用于定位和辅助去重，不宣称它单独实现了历史变更同步。

### G05：手动备份与 App 内保护副本的区别

现状：已设计用户主动导出的备份和恢复前的内部保护副本，但用户可见的保存位置、最近成功备份状态与两者的保留边界没有完整说明。

事实：Android 在卸载应用时会删除 App 专属存储中的文件，因而内部独立目录不等于独立于 App 的备份。[Android 官方存储说明](https://developer.android.com/training/data-storage/app-specific)

建议：

- 手动备份通过系统选择器保存到用户选择的本地、可见文档位置。
- 内部保护副本明确用于恢复回退，可从备份页导出；不能将其描述成卸载后仍可保留的外部备份。
- 设置中显示“最近一次成功导出备份”的时间和可用文件信息；该时间不意味着此后新增数据也已备份，更不保证用户没有移动或删除文件。
- 不默认加入自动备份、定时通知或云同步。

### G06：返回、中断与保存失败

现状：已确认退出未完成输入不生成正式记录、不持久保留草稿，但缺少各个状态下返回和恢复的细则。

建议补齐：

- 每次新记账金额为空并聚焦金额输入，日期为当前日期时间；不把演示值或上一笔金额自动带入。
- 关闭小类弹层回到金额页，保留当前输入。
- 短暂切到后台且进程仍在时保留正在输入的界面；系统终止后不承诺恢复未保存输入，已保存记录必须完整。
- 写入失败不回首页、不清空输入，明确提示未保存并允许重试；继续使用同一提交标识防重复。
- 键盘、分类弹层与金额页的系统返回顺序写入交互规格。

### G07：大类变多、长名称和大金额

现状：原型展示三个短名大类，正式页面的输入长度、金额上限和内容过长时的展示规则尚未量化。

建议补齐：大类列表可滚动且底部导航保持可用；保存回首页保留合适的滚动位置；长名称、长金额和大字体仍可读，金额不静默截断或丢失小数；名称、备注长度及金额边界在输入规格中给出具体上限和提示。

这些是组件与数据边界规格，不需要用户逐项决定数据库类型或字符长度。任何建议的输入限制在页面规格中写清，不暗中改变已确认的精度与币种。

### G08：跨月刷新与统计范围说明

现状：已计划月边界计算测试，但没有明确 App 长时间在前台或后台跨月时的刷新触发。

建议：默认本月模式在日期变化或回到前台时重新确认当前月份并刷新；不能只等数据库新增记录才更新。若 G01 采用历史月浏览，则用户主动选中的历史月份保持不变。

停用大类仍计入总计是已确认规则；当可见卡片合计与顶部总计不同，应能从明细或简短说明中理解统计包含停用分类历史，不改变现有统计口径。

## 5. 可选扩展，非开工必需条件

- **支付方式**：若后续确实需要分析微信、支付宝、银行卡、现金占比，应现在决定是否增加结构化字段；这会影响已定 Excel 模板。现有首版没有账户余额管理要求，不自动加入。
- **指纹锁 / 备份加密**：目前未作为需求确认。现有技术草案没有备份密码流程，这仍是技术建议，不等于用户已提出或逐项确认隐私功能。若需要，应在界面与备份格式锁定前评估；不把它们默认当成首版必做项。

退款、云同步、多币种、复杂图表等已有范围决定，不在本次审查中重新发起确认。

## 6. 对计划的影响

- 本次只登记分析，不安装工具链、不创建 App 工程、不修改 Excel 模板，也不将 G01—G03 自动写入需求基线。
- G01—G03 选择后，更新需求和对应验收；G04—G08 在相关页面与文件实现前形成明确规格与验证场景。
- 工具链等技术准备与这些选择可独立进行；当前用户要求先做审查，因此本轮止于提供审查结果。
